# Research: should agents get a committed index of every file?

Date: 2026-11-18. Outcome: [no committed file index](../decisions/2026-11-18-no-committed-file-index.md).

## The question

The reference workflow this project is distilled from kept a generated `FILES.md`: one entry per file, holding the summary from the file's header comment, its line count and its test. It was regenerated by every PR and committed with it. After about two months it was 270 KB. Does an index like that make coding agents faster or better, and is it worth what it costs a team?

## What the evidence says

1. **Repository overview files do not reduce agent steps.** Gloaguen et al., *Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?* (ETH Zurich and LogicStar.ai, [arXiv:2602.11988](https://arxiv.org/abs/2602.11988), ICLR 2026) tested Claude Code, Codex and Qwen Code with and without context files:
   - LLM-generated files lowered task success slightly. Developer-written files gave a modest gain.
   - Inference cost rose by more than 20%.
   - Context files "do not effectively serve as repository overviews": they did not reduce the steps agents took to reach the relevant files.
   - The files helped when they stated **non-standard conventions** the agent could not infer. The authors recommend that human-written files describe only minimal requirements.
2. **On-demand search beats a preloaded index for live codebases.** Claude Code's team tried RAG over a local vector index and moved to agentic search (`glob`, `grep`, `read`). Their reasons: an index goes stale with every edit, needs infrastructure, and the model can reason about where code lives and verify it in a few calls. Critics point out the token cost of grep-only search on very large repositories, which is where a *ranked, budgeted* map can help.
3. **When a map helps, it is ranked and budgeted, not exhaustive.** Aider's repo map parses symbols with tree-sitter and ranks them by references (PageRank). It then fits the map to a token budget of roughly 1–4k tokens and recomputes it for the task at hand. It is never a full listing, and it is never committed.
4. **Context is a budget.** Anthropic's guidance on context engineering: keep the smallest set of high-signal tokens, retrieve just in time, and let lightweight identifiers (paths, names, folder structure) stand in for content until it is needed.

## What this means for a committed FILES.md

| Property | Committed full index | Evidence |
|---|---|---|
| Helps the agent find files | marginally; agents still search | 1, 2 |
| Context cost | grows with the repo, paid by every session that reads it | 1, 4 |
| Freshness | stale between regenerations; wrong on any branch that has not regenerated | 2 |
| Team cost | conflicts on every pair of parallel PRs; needs a merge driver plus a regeneration step after every merge | the reference workflow's own history |
| What it really carried | the per-file **header**, which `grep` finds without the index | n/a |

The valuable part was never the index. It was the discipline of a 1–3 line header in every file, plus knowing which test covers which file. Both survive without a committed artifact.

## Recommendation

1. **Keep file headers.** They are local, cheap, read only when the file is opened or grepped, and never conflict. `doctor` asks for them on **new** files only, so it never blocks.
2. **Generate maps on demand.** `agent-os map [path] [--budget N]` renders one area (headers, sizes, covering tests, recently changed files), cached per commit in `.agent-os/cache/` (gitignored). Later, an optional ranked symbol map in the style of Aider for very large repositories.
3. **Keep a small hand-written area map** in `AGENTS.md`: one line per top-level area ("`src/billing/`: invoices and payment providers"). That is the non-standard knowledge an agent cannot infer, and the kind of content the study found useful. `doctor` checks that every top-level source directory is listed.
4. **Measure it.** Skill evals (v1.0) compare the number of steps and tokens per task with and without `map`, so the feature has to earn its place.
