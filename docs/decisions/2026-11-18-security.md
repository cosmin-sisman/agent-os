# Security: watch, check and prepare, integrated into the flow

Status: accepted

## Context
Security work is usually either forgotten or a one-off scan. Advisories appear daily, but only a few concern a given project. Code written by agents needs the same scrutiny as any other code, and teams rarely prepare attack scenarios before an incident.

## Decision
- **Watch:** authoritative advisory sources (GitHub and GitLab advisory databases, OSV, NVD, CISA KEV, stack vendors, OWASP), filtered by lockfiles, an SBOM and `stack.yaml`, prioritized by exploitation (KEV, EPSS), severity and reachability. A scheduled job maintains one Security digest issue. Only package names and versions leave the project.
- **Check:** a layer-based pass in every change request through the `security-review` slot, using OWASP ASVS checklists and the results of existing scanners (secret scanning, dependency audit, CodeQL, GitLab SAST or Semgrep, container and IaC scanners) when present.
- **Prepare:** threat models per layer as living artifacts, abuse cases added to test plans for sensitive areas, a security regression test for every fix, and tabletop exercises on demand.
- **Report safely:** vulnerabilities go to private channels (draft security advisories on GitHub, confidential issues on GitLab). Scenarios run only against environments the project owns.
- **Gate:** `/release` refuses known-exploited vulnerabilities in shipped dependencies without a written risk acceptance.

## Consequences
Security becomes continuous and specific to the project, and it costs little attention when nothing relevant happens. It depends on external sources being reachable; on air-gapped self-managed installs the watch uses an internal mirror or is disabled with a visible warning.
