# The stack map: layers as the backbone

Status: accepted

## Context
Projects differ mostly by their stack. A team already reasons about it in layers (frontends, APIs, services, workers, data, auth, payments, delivery), often in a spreadsheet with technologies, providers and scores. The agent system needs the same knowledge to label work, choose tests, check the environment and recall lessons, but it had no structured source for it.

## Decision
- agent-os ships a catalog in YAML: layers, technologies (with complexity and AI-friendliness), languages, providers (with ease, cost, EU regions and an MCP hint), runtimes and ten blueprints by level, all bilingual (en, ASCII ro). Projects extend it in `.agent-os/catalog/`.
- Each project has one committed `stack.yaml` mapping layers to technology, provider, status, paths, owners and notes, written in a dependency-free YAML subset.
- Layers become the `area:*` labels. Their paths feed the gate, overlap, `/next`, lessons recall and the AGENTS.md area map. Providers and technologies propose `requires` entries for `/env`.
- Changing a layer is a decision: `stack set` writes the record with the catalog's comparison.
- `stack detect`, `drift` and `import` bring existing repositories and spreadsheets in.

## Consequences
The stack stops being tribal knowledge. Labels, tests, environment checks and lessons all speak the same vocabulary. Catalog scores are indicative and editable, so they inform decisions without deciding them.
